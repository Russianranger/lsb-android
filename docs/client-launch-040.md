# Prepared-client launch · 0.4.0

Milestones 1 and 2 are accepted on the Thor: the independent Windows runtime, followed by registration and actual COM construction using the imported US client. This build adds the next device test: execute that installation's xiloader, authenticate to the existing Termux server and attempt character/world entry. Actual game compatibility remains a device acceptance item.

## Device procedure

1. Install `LSB-Android-0.4.0.apk` over the current app. Keep the activated 0.3.0 preparation and Turnip 26 setting. No re-import, preparation copy or runtime download is required.
2. Start the existing LandSandBoat server in Termux as usual.
3. Open **Client → Play FINAL FANTASY XI**. Leave **Server address** as `127.0.0.1` for that server, enter your existing server account/password, and tap **Launch FFXI**. Account creation, password changes and OTP enrollment are not provided in this baseline.
4. The app checks the prepared files, imported loader's command-line markers and DLL dependencies, then starts xiloader inside the existing display. A blank desktop during startup is possible. **Back** returns to the app while the runtime continues; **Open client display** reconnects. **Stop** ends the owned Wine session.
5. If character selection appears, enter an existing character and check whether the world renders and movement/audio work. Exit normally if possible; otherwise use **Stop**. Export **Diagnostics → Export support ZIP** and report the last visible stage. Account/password must be entered again for another launch.

If startup stops at the dependency check, **View launch results** lists each DLL and its Windows error. Send that report before installing unrelated components. The accepted client DLL registration required no extra installer; the imported xiloader has separate Visual C++ imports.

## Targeted prerequisite recovery

If a loader dependency is missing, expand **Preparation and recovery**, use **Select launcher prerequisite (.exe)** for its official x86 installer, then **Repair launcher prerequisites**. This copies the activated working client (including its current user settings) and prefix into a separate candidate before running the interactive installer. Allow enough storage for that full recovery copy; the requirement is checked before copying. No credentials are needed for repair and repair never logs in automatically.

Repair repeats the registration/COM checks and the loader dependency check. It activates the candidate only after the entire operation succeeds. The previous client/prefix pair remains available through **Restore previous preparation**. An interrupted or failed repair leaves the accepted preparation selected. A complete repair candidate is reused on retry. An unrelated pending preparation must be explicitly discarded before starting a launcher repair. Existing session backup ZIPs still contain the source import rather than the prepared runtime generations.

## Launch and diagnostic boundaries

- Launch uses the selected, previously accepted generation directly. It does not rewrite registration, replace xiloader, run GameHub or change the Termux server. Ordinary client writes remain in the working installation/prefix.
- The existing source inventory and actual key-file hashes are revalidated. The exact loader SHA-256 is recorded. Static inspection requires `--server`, a supported account/password alias and `--lang`; it prefers the historically used `--username`/`--password` spelling. Marker inspection is evidence of those strings, not proof that every executable implements the same parser. The device login test still verifies the imported binary's behavior.
- A separate x86 helper asks Windows to load each normal-import DLL from the loader directory/system search path, recording its loaded path or error. This catches missing/transitively missing DLLs and architecture failures. It does not prove delayed imports, every required export or full Visual C++ behavioral compatibility. Subsequent process creation/exit is recorded separately with the full Windows code, including values such as `0xc0000135` that Unix exit status would truncate.
- The native worker uses explicit `CreateProcessW` application and working-directory paths. The working directory is the imported loader's own directory, including its neighboring bootloader files. Arguments use CRT-compatible quoting and the selected preparation's language; no CMD, shell interpolation, `--hide` or automatic hairpin override is used. Test fixtures include spaces in the loader path and quotes, spaces, backslashes, `%`, `!` and `&` in a password.
- Account/password fields are not saved to preferences, Android instance state, launch JSON, Intent extras or support bundles. A short-lived one-use in-process ticket passes them to the service. They then cross anonymous pipes into the native worker; the worker supplies the required Windows CLI in memory and clears its staging buffers. The loader necessarily holds its own credentials/CLI while authenticating; this is not protection against a privileged debugger. ASCII account/password input is supported in this baseline, without silent trimming of secrets.
- Once credentials can reach Wine, arbitrary child output is discarded before persistence. Only fixed event names are retained, so split, escaped, colored or UTF-16 credential echoes cannot enter logs. DLL-check output precedes credential delivery and remains available for diagnosis. The PRoot wrapper's raw stream is discarded for login because fatal tracee diagnostics can contain command lines. DXVK's direct launch log output and Wine crash-debugger invocation are disabled for the login process. No raw console transcript or screenshots are included in support exports.
- `client_running` means the Windows loader process is alive. A zero exit means it closed normally. Neither automatically asserts authenticated login or world entry; those remain explicit device observations. If login falls back to an interactive menu, use **Stop** and correct the Android fields for another attempt.

## Sources and verification

Historical invocation evidence is recorded in [working-setup.md](working-setup.md). The command aliases and numeric language mapping were checked against [LandSandBoat/xiloader main.cpp at 370a1a1](https://github.com/LandSandBoat/xiloader/blob/370a1a11e4d3c5b58b793bd83096de34d5942ed6/src/main.cpp). That source is newer than the user's reported v2.0 and is not treated as proof of its complete protocol or parser. Explicit application-path and mutable-command-line behavior follows [Microsoft's CreateProcessW documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw).

Local checks cover recovery-copy isolation, one-use credential transport, input rejection and private output filtering. ARM64 Wine/PRoot fixtures exercise launch/relaunch, literal argument transport, working directory, full Windows failure codes, missing dependencies and Stop. Fixtures contain no game data and never contact a server. See [validation.md](validation.md) for the completed gates and APK identity. Existing RpcSs/libXcomposite warnings are carried forward from the accepted preparation; this build does not replace the tested runtime to suppress them.
